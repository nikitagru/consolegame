> Траектория для Java-разработчика с опытом backend-разработки и нулевым опытом в C++.  
> Ориентир по нагрузке: **10–15 часов в неделю**.  
> Длительность базовой программы: **24 недели**.

---

## Цель программы

К концу плана у вас должен быть не набор повторённых туториалов, а законченный вертикальный срез небольшой игры: с управлением, боевой системой, AI, UI, сохранениями, уровнями, тестами и собранным билдом.

Подход:

- Сначала — достаточная база современного C++.
- Затем — Unreal Editor, Blueprints и Unreal C++.
- Все темы сразу закрепляются в одном учебном проекте.
- Код отвечает за правила и устойчивую логику, а Blueprints — за быстрые настройки, визуальную композицию и контент.
- Каждую неделю должен появляться проверяемый результат: коммит, видео, GIF, тестовая карта, фича или билд.

# Учебный проект: Rift Runner

## Концепция

**Rift Runner** — компактная 3D action-roguelite / top-down shooter игра.

Игрок управляет инженером, исследующим боевые арены с энергетическими разломами. Во время забега он:

- передвигается, прыгает или выполняет рывок;
- стреляет из нескольких видов оружия;
- сражается с дронами;
- собирает энергию и улучшения;
- активирует генераторы или зачищает волны врагов;
- переходит между аренами;
- после смерти видит результат и может начать новый забег;
- сохраняет рекорд, разблокированные улучшения и пользовательские настройки.

## Почему именно этот проект

Он небольшой по объёму контента, но покрывает ключевые системы Unreal Engine:

- игровой персонаж и камера;
- input и движение;
- коллизии, физика и hit detection;
- оружие и снаряды;
- AI и навигация;
- UI/HUD;
- звук и VFX;
- Gameplay Framework;
- data-driven design;
- сохранения;
- уровни и performance profiling;
- packaging;
- в расширенной версии — Gameplay Ability System или сетевой режим.

## Границы проекта

На первом проходе **не нужно** делать:

- открытый мир;
- PvP;
- полноценный кооператив;
- процедурную генерацию уровня уровня Hades;
- реалистичную графику;
- десятки типов оружия и врагов.

Цель — завершённый vertical slice, а не бесконечный долгострой.

# Этап 3. Фундамент Rift Runner

## Неделя 7. Gameplay Framework

### Теория

Разобрать назначение классов:

- `GameMode` — правила игрового режима;
- `GameState` — общее состояние забега или матча;
- `PlayerController` — управление игроком и координация input/UI;
- `Pawn` / `Character` — игровое воплощение;
- `PlayerState` — состояние игрока;
- `HUD` — UI-представление;
- `GameInstance` — данные между уровнями в одном запуске.

### Практика

Создать:

```text
ARiftRunnerGameMode
ARiftRunnerCharacter
ARiftRunnerPlayerController
ARiftRunnerPlayerState
ARiftRunnerGameState
```

Реализовать:

- здоровье, энергию и смерть персонажа;
- перезапуск забега;
- счётчик уничтоженных врагов;
- тестовый HUD: `Health`, `Energy`, `Score`;
- назначение своего `GameMode` для карты.

### Архитектурное правило

Не помещать правила забега в `Character`. Например, «волна завершена» — ответственность `GameMode`/`GameState`, а не игрового персонажа.

## Неделя 9. Компоненты и система урона

- события и delegates.

### Практика

Создать:

```text

UDashComponent
UWeaponComponent

```

Требования:

- `UHealthComponent` отвечает только за здоровье, смерть и события изменения здоровья;

- UI подписывается на события, а не опрашивает значения на каждом `Tick`.

# Карта Java → Unreal C++

| Java / backend-опыт | Unreal C++ / Engine | Что важно учитывать |
|---|---|---|
| Spring-сервисы и компоненты | `ActorComponent`, `GameInstanceSubsystem`, `WorldSubsystem` | Нет привычного DI-контейнера; критичен lifecycle Engine/World |
| REST DTO | `USTRUCT`, Data Assets, Data Tables | Данные должны быть отражены через Unreal Header Tool |
| Interfaces | `UInterface`, delegates, Event Dispatchers | Unreal-интерфейс состоит из `UInterface` и C++ части |
| JUnit | Unreal Automation Tests | Логику полезно выносить из Actor в тестируемые классы |
| Maven / Gradle | Unreal Build Tool, `.Build.cs`, `.uproject` | Зависимости и модули устроены иначе |
| JVM GC | Unreal GC + C++ RAII | `UObject` управляется UE GC, обычные C++ объекты — C++ lifetime |
| SLF4J / Logback | `UE_LOG` | Логи строятся вокруг категорий UE |
| Конфиги и профили | Project Settings, `.ini`, Data Assets | Баланс и контент стоит отделять от кода |

# Ключевые правила C++ в Unreal

1. Не использовать `std::shared_ptr` для `UObject`.
2. Не удалять `UObject` вручную через `delete`.
3. Для Unreal-объектов использовать типы и паттерны UE.
4. Для чистой независимой логики применять современный C++ и RAII.
5. Не помещать всю логику в `Character.cpp`.
6. Предпочитать компоненты, интерфейсы, delegates и data-driven конфигурацию.
7. Не использовать `Tick` как универсальное решение: предпочитать события и таймеры.
8. Сначала делать работающую игровую петлю, потом усложнять архитектуру.

# Главный принцип

Не пытайтесь сначала построить идеальную универсальную архитектуру. В gamedev ценность появляется через короткие итерации:

```text
Игрок движется → стреляет → попадает →
получает понятную обратную связь → завершает игровой цикл уровня.
```

Только после того, как механика работает, нужно улучшать её структуру, устранять дублирование и добавлять обобщения.
